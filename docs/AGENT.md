# 编程 Agent 工作规范(注意全程按照spec.md来实现)
开始任务前读取本文件和 request.md以及spec.md。不同工具的规则文件加载方式不同；未自动加载本文件的工具，需要在任务提示词中显式引用。
遵守运行工具的上层指令与约束。用户当前明确指令优先于本文件中的项目约定；已有授权继续有效，不重复索要确认。

## 1. 围绕需求工作
- 以用户当前任务和需求文档的验收标准为依据，只完成必要范围，不顺手重构或增加功能。
- 基础版先完成 P0；可选重置功能和后续拓展需要用户选择，不提前实现。
- 优先保证演示可运行、代码可理解、结果可验证。技术选型服务于当前问题，不以框架、模型或代码数量体现完成度。
- 缺少会影响实现方向的关键信息时，提出具体问题；普通实现细节自行判断，并简要说明重要取舍。
- 简单任务直接处理；较复杂任务先给简短计划，拆成可独立验收的小需求。不要为简单改动额外创建规格、计划或总结文档。
## 2. 每个需求的工作流程
1. **读取上下文**：检查需求、相关代码、现有文档、当前分支和 Git 工作区，区分已有改动与本次改动。
2. **明确验收**：说明要解决的问题、涉及范围和成功标准，再选择最小可行实现。
3. **小步实现**：一次处理一个逻辑需求，保持前端、接口、仿真规则和对应测试一致。
4. **验证与审查**：执行与改动有关的检查，对照验收标准检查结果，并审阅实际 diff。
5. **保存检查点**：需求完成且相关检查通过后，暂存本需求的改动并创建本地 Git 提交，再进入下一个需求。
同一个需求所需的前端、后端、测试和说明可以放在同一次提交中。无法独立运行或验证的零碎步骤不应被当成已完成需求。

## 3.我的要求实现（重要务必看）

## 4. Git 分支与提交
### 4.1 合理使用分支
- 开始前检查当前分支、未暂存改动和已暂存改动，不覆盖、清理或夹带用户及其他协作者的工作。
- 默认分支以仓库设置为准。开发任务使用工作分支，除非用户明确要求，否则不直接在默认分支开发或提交。
- 已处于适合当前目标的工作分支时继续使用；新的独立目标另建分支。一个目标可包含多个需求和多次提交，无需每次提交都新建分支。
- 分支名采用用途前缀和简短英文描述，例如 `feat/manual-control`、`fix/move-validation`、`docs/agent-rules`。
- 不为切换分支丢弃现有改动；遇到无法安全处理的交错改动，先说明具体冲突。
### 4.2 每完成一个需求，留下一次本地记录
本项目将「暂存一次 Git 记录」落实为：**完成需求 → 验证通过 → 审阅 diff → 暂存相关改动 → 检查暂存内容 → 创建本地 commit**。
- `git add` 仅进入暂存区，`git commit` 才形成可回溯的版本；`git stash` 用于临时收起工作，不能替代需求完成记录。
- 在开始下一个需求前提交当前已完成需求，不把多个无关需求累积成一个大提交。
- 只暂存本需求涉及的文件或代码块，避免无差别执行 `git add .` 或 `git add -A`。
- 提交前检查暂存区，确认没有无关文件、密钥、生成物或他人改动。已有不属于本任务的暂存内容应保持原样，不能混入本次提交。
- 未通过相关检查时先修复，不将需求标记为完成，不用空提交制造进度。
- 用户当前明确禁止提交或限制 Git 操作时，按该限制执行，并在结果中说明哪些改动尚未提交。

### 4.3 提交信息

采用 `type(scope): 简短中文说明`，`scope` 可省略。说明具体变化，避免仅写 `update`、`修改代码` 或 `完成任务`。

|类型|用途|
|---|---|
|`feat`|新功能。|
|`fix`|修复错误。|
|`docs`|文档变更。|
|`test`|测试变更。|
|`build`|构建、依赖或容器构建配置。|
|`ci`|自动化检查与工作流。|
|`refactor`|保持行为不变的重构，仅在任务范围需要时使用。|

示例：

```
feat(simulator): 支持机器人四方向移动
fix(api): 拒绝无效的移动方向
docs: 补充本地启动说明
ci: 添加 Go 测试与构建检查
```

必要时在提交正文说明原因和验证方式，不记录未执行的测试或未完成的功能。

### 4.4 远程与历史操作
- 本地提交不等于授权远程发布。推送、创建 PR、合并和部署按用户已有授权执行，不擅自扩大范围。
- 未经授权不重写历史、强制推送或执行会丢弃改动的操作，不修改 Git 全局配置和远程地址。
- 交付时说明工作分支和本次提交记录，便于人工审查和回溯。

## 5. 测试与代码审查
- 测试覆盖规则和行为，包括正常移动、边界、障碍物、非法请求及失败后状态不变，避免只验证实现细节。
- 页面交互改动应在浏览器中检查真实 API 请求、状态更新和失败提示，不能仅凭页面截图判断前后端已联通。
- Docker 和 CI 的变更分别验证相应行为。本地检查通过不代表远程 CI 已通过，镜像构建成功不代表服务已部署。
- 纯文档任务检查内容、路径和格式即可，不运行无关的 Docker 检查。检查已通过且没有新改动或疑点时，不反复运行。
- 自查时对照 diff 和验收标准，关注回归及遗漏。用户要求独立审查时，再安排相应审查；多个 Agent 得出相同结论不能替代测试证据。
- 权限、重要数据和发布操作需要明确责任与授权。自动化检查、独立审查和人工判断分别提供证据，不能相互替代。
- 工具或环境不可用时如实说明未验证项，不伪造输出，不为通过检查擅自安装全局依赖或修改系统配置。

## 6. Skill 与文档维护
- 使用与任务相关的 Skill 前读取其说明，并简要告知用途。不为了套用工作流扩大任务范围，也不把其他项目的示例当成本仓库要求。
- 需求文档负责范围与验收，README 负责用途与运行入口，必要的详细说明放在 `docs`。按实际需要维护，避免重复文档。
- 修改 API、启动方式或用户可见行为时，同步相关说明；不能为迁就实现或测试悄悄改写需求。
- 文档区分已实现、计划中和未验证的内容，不把建议写成既成事实，不保留已否决或已删除方案的解释性痕迹。
- 不提交凭据、令牌、私钥、本地环境文件、编译产物或无关大文件。

## 7. 沟通与交付
- 使用简洁中文，优先保证准确性，区分事实、推测和建议，避免夸赞、空泛承诺和无依据结论。
- 调用工具前简述动作和目标；持续工作每完成一个阶段或约 60 秒汇报一次有意义的进展。
- 需要用户手动执行命令时，每次只提供一条命令，不安排重复且无意义的验证。
- 本地操作遵循实际 windows 环境；Linux 容器或远程任务在相应环境中执行，不修改本机兼容层或全局配置。
- 最终说明实际改动、验证结果、分支与提交记录，以及必要的未验证项。只报告实际完成的工作。
